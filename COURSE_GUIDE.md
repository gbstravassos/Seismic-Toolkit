# Course guide: how to learn and deliver

## Learner profile

This course assumes you can already write Python functions and classes, use NumPy arrays, create plots and understand basic scientific computing. It does **not** assume experience shipping packaged software, reviewing pull requests, using large language models for coding, or evaluating ML models on correlated observations.

## Daily learning routine

For a 6–8-hour weekly budget, use three study sessions of 2–3 hours. In the first session, read the notebook and execute each worked example. In the second, write failing tests and implement the week's challenge; use a debugger rather than repeatedly guessing. In the third, attempt the applied problem, document your assumptions and perform a code review. Keep a short `LEARNING_JOURNAL.md` locally if useful.

Do not start with the reference solution. If you are blocked, use the hints in the corresponding `exercises/weekXX.md` document. After solving, compare the structure and test coverage with the reference implementation, not merely whether the numerical outputs match.

## Where each kind of code belongs

| Code type | Location | Why |
|---|---|---|
| Reusable numerical algorithms | `src/seismic_toolkit/` | Importable, testable, shared by scripts/UI |
| Student implementations | `src/seismic_toolkit/challenges.py` | Evaluated independently |
| Assertions about behavior | `tests/` | Runs automatically and reproducibly |
| Investigation, charts and theory | `notebooks/` | Interactive exploration |
| Application interface | `apps/` | User interaction separated from math |
| Reports generated by local runs | `outputs/` | Not committed by default |
| Prompts and engineering notes | `resources/` | Auditable reasoning and safe reuse |

## Git workflow

Each week create a dedicated branch, update the function and tests, and commit with a clear message. Example:

```bash
git switch -c feature/week03-moving-rms
python -m pytest -o addopts='' -m exercise -k week3 -q
python -m pytest -q
git add src/seismic_toolkit/challenges.py tests
# You may also add your own new tests
git commit -m "feat: implement centered moving RMS with edge handling"
```

Add a short PR description: problem solved, design assumptions, tests and their output, limitations, and whether AI-generated code contributed to the patch. Avoid including private data, credentials, or giant notebook outputs.

## Windows tips

If PowerShell rejects `.venv\Scripts\Activate.ps1`, you can run the venv executables directly (`.venv\Scripts\python.exe -m pip ...`) or configure the PowerShell execution policy according to your organization's IT rules. Do not blindly disable security controls. In VS Code, use **Python: Select Interpreter** and choose `.venv`; in the notebook, choose the matching kernel.

If `python` or `py` commands differ on your PC, use the interpreter recognized by your virtual environment. After installing editable mode, restart the notebook kernel if imports still point to an older copy.

## Troubleshooting

- **`ModuleNotFoundError: seismic_toolkit`:** activate `.venv`, run `python -m pip install -e '.[course,dev]'`, select that interpreter as the notebook kernel.
- **Tests fail in `challenges.py`:** expected before assignments are implemented; `python -m pytest -q` excludes them, while `-m exercise` runs them intentionally.
- **Jupyter cannot find notebook files:** launch from the project root with `python -m jupyterlab`.
- **`streamlit` not installed:** run `python -m pip install -e '.[app]'` before launching the optional UI.
- **Slow ML cross-validation:** use fewer groups/samples or lower fold count while debugging, then restore the expected defaults.
- **Invalid data error:** inspect array dimensionality, finiteness, sampling units and group labels before modifying algorithms.
- **Git push says `Repository not found`:** check that the repository exists on GitHub, credentials permit access, and `git remote -v` points to the exact correct URL.

## Integrity and responsible AI use

A passing test does not prove scientific correctness; design tests around assumptions and known examples. Do not claim synthetic results reflect operational reservoir quality. Use LLMs for explanation, test generation or candidate changes, but read every change and keep a record of validation. Share only materials permitted by the data owner and organizational policy.

## Recommended weekly evidence

Keep a brief log: feature branch and commit ID, completed tests, screenshot or output of the relevant figure, an explanation of one edge case, one limitation, and a proposed next enhancement. This becomes an engineering portfolio without needing to expose any workplace material.
